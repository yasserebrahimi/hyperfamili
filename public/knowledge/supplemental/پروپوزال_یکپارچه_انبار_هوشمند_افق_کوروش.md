01. خلاصه مدیریتی

ضرورت پروژه

افق کوروش و اکالا در نقطه‌ای قرار دارند که انبار و زنجیره تأمین دیگر صرفاً مرکز هزینه نیست؛ بلکه موتور رقابت در قیمت، SLA، دسترسی‌پذیری کالا و تجربه مشتری است. پروژه مدیریت هوشمند انبار باید سه مسئله را همزمان حل کند: سرمایه در گردش، دقت عملیات و سرعت پاسخ به تقاضا.

در بافت ایران، مسئله از یک پروژه کلاسیک automation فراتر است. تورم، نوسان نرخ ارز، مناسبت‌های شمسی/قمری، رفتار خرید هیجانی، محدودیت GPU و دسترسی محدود به SaaSهای خارجی باعث می‌شود نسخه بومی پروژه باید self-hosted، داده‌محور، resilient و مرحله‌ای باشد.

تز اصلی

رباتیک سنگین در فاز اول توصیه نمی‌شود، مگر در zoneهایی که volume/density/throughput و قابلیت نگهداری آن با داده واقعی اثبات شده باشد. بهترین شروع، ترکیب این سه محور است:

Forecast + Replenishment: پیش‌بینی تقاضای تورم‌محور، safety stock پویا و سفارش‌گذاری پیشنهادی.

WMS Intelligence: dynamic slotting، wave/batch picking، pick path optimization و کنترل FEFO.

Operational Visibility: داشبوردهای عملیاتی، data quality، Edge Vision محدود و alerting.

بخش ۳ — منطق تصمیم راهبردی: Option A در برابر Option B

این بخش، چارچوب تصمیم سرمایه‌گذاری برای هیئت‌مدیره است. صورت‌مسئله دو مسیر هم‌زمان دارد: یک مسیر متمرکز و شش‌ماهه برای افق کوروش + اکالا + انبارهای فعلی، و یک مسیر بزرگ‌تر برای تحول کل اکوسیستم گلرنگ.

تعریف دو گزینه

Option A — ستون فقرات داده، تصمیم و اتوماسیون برای افق کوروش/اکالا. ساخت لایهٔ داده، پیش‌بینی، Control Tower، مسیرسازی و بهینه‌سازی عملیات برای شبکهٔ فعلی، به‌گونه‌ای که در شش ماه به وضعیت implementation‑ready برسد و سپس از ماه دوازدهم به‌صورت stage‑gated به سمت Option B گسترش یابد.

Option B — تحول کل اکوسیستم گلرنگ به یک «سیستم‌عامل سازمانی» (Enterprise Operating System). تعمیم داده، فرایند، حاکمیت، Control Tower و MLOps از retail و e‑grocery به تولید، توزیع، خدمات مالی، سلامت و سایر شرکت‌های گروه. این یک برنامهٔ operating‑model transformation است، نه صرفاً یک پروژهٔ IT.

از منظر مقیاس، گلرنگ در وب‌سایت رسمی خود به بیش از ۱۴۰ برند کالای تندمصرف، ۷۳ برند دارویی فعال و بیش از ۱۲۵ شرکت در حوزه‌های تولید، بازرگانی و خدمات اشاره می‌کند و در بخش فناوری شرکت‌هایی مانند گلرنگ سیستم و واحدهای فناوری مرتبط را فهرست کرده است (منبع: golrang.com). همین گستردگی توضیح می‌دهد که چرا Option B بالقوه ارزش‌آفرینی بالاتری دارد، اما از نظر حاکمیت داده، استانداردسازی فرایند، MDM و مدیریت تغییر نیز به‌مراتب پیچیده‌تر است.

توصیهٔ نهایی

اکنون Option A را تصویب کنید؛ معماری و حاکمیت آن را از روز اول با قابلیت scale‑out برای Option B طراحی کنید؛ و ورود به Option B را به عبور از gateهای ماه ششم و دوازدهم مشروط سازید.

این توصیه سه دلیل اصلی دارد:

زمان تا ارزش (Time‑to‑Value): در Option A کوتاه‌تر است؛ لایه‌های داده، پیش‌بینی، Control Tower، مسیرسازی و بهینه‌سازی عملیات را می‌توان بدون انتظار برای یکسان‌سازی کل هلدینگ به تولید رساند.

شدت CapEx و وابستگی به سخت‌افزار وارداتی: در Option A پایین‌تر و کنترل‌پذیرتر است — موضوعی که در محیط تورمی و محدودیت‌های تأمین ایران اهمیت مضاعف دارد.

قابلیت استفادهٔ مجدد معماری: پشتهٔ پیشنهادی Option A (Kafka، Spark، Iceberg، ClickHouse، Feast، MLflow، Kubernetes/K3s، MQTT، Redis، DataHub) ذاتاً قابل‌گسترش به کل گلرنگ است و باید از ابتدا با یک Design Authority مشترک ساخته شود، نه به‌عنوان راهکار موضعی.

این الگو با مسیر جهانی موفق هم‌راستاست: بسیاری از شرکت‌ها ابتدا از داده، تصمیم‌گیری و سنسوری‌سازی شروع کرده‌اند و بعد به سراغ مکانیزاسیون سنگین رفته‌اند. برای نمونه، Walmart به‌طور عمومی اعلام کرده که در حال گسترش استفاده از سنسورهای ردیابی برای ده‌ها میلیون پالت در زنجیرهٔ آمریکاست و هم‌زمان همکاری خود با Symbotic را برای اتوماسیون توسعه داده است (منبع: Financial Times).

جمع‌بندی مالی برای هیئت‌مدیره

در قیمت ثابت ۱۴۰۵ و به‌صورت سناریویی:


| گزینه | اندازهٔ تقریبی برنامهٔ ۳۶ ماهه | نقطهٔ سربه‌سر (سناریوی پایه) |
| Option A | ۱٬۳۰۰ تا ۲٬۰۰۰ میلیارد تومان | ۲۰ تا ۲۴ ماه |
| Option B | ۴٬۲۰۰ تا ۶٬۶۰۰ میلیارد تومان | ۳۰ تا ۳۴ ماه |

01. مدل عملیاتی هدف برای افق کوروش و اکالا

مدل هدف

مدل عملیاتی هدف از چهار لایه تشکیل می‌شود:

Control Tower: دید لحظه‌ای/روزانه از موجودی، سفارش، انبار، اکالا، ناوگان، SLA و استثناها.

Decision Engines: موتورهای forecast، replenishment، slotting، picking، packing، dispatch، route، ETA و workforce.

Execution Apps: اپلیکیشن مدیر انبار، picker، packer، driver، مدیر شعبه و dashboard مدیرعامل.

Governance & Feedback: پایش KPI، model drift، data quality، human override، audit log و retraining.

اصل O2O

افق کوروش فروشگاه فیزیکی گسترده دارد و اکالا بازوی دیجیتال است. بنابراین طراحی نباید فقط انبار مرکزی باشد؛ بلکه باید فروشگاه، قفسه، دارک‌استور و لجستیک آخرین‌مایل را در یک حلقه داده‌ای ببندد.

جریان تصمیم


| ورودی | موتور تصمیم | خروجی عملیاتی |
| POS + اکالا + تقویم + اقتصاد کلان | Forecasting | پیش‌بینی تقاضا در سطح SKU/Store/Day |
| Forecast + موجودی + lead time | Replenishment | سفارش پیشنهادی شعب و دارک‌استور |
| Orders + layout + SKU location | Picking optimizer | wave/batch و مسیر picker |
| Routes + vehicles + windows | TMS/VRP | manifest و ترتیب تحویل |
| CCTV/IoT/RFID | Edge Intelligence | هشدار قفسه/ایمنی/سردخانه |
| KPI + drift | MLOps | بازآموزی و اصلاح مدل |


02. معماری کلان End-to-End

دیاگرام Mermaid

flowchart LR
  ERP[ERP/GNG/Dynamics] --> CDC[Debezium CDC]
  WMS[WMS] --> API[Integration APIs]
  POS[POS شعب] --> Agent[Store-and-Forward Agent]
  OKALA[Okala App/Web] --> Kafka[Kafka/Redpanda]
  CCTV[CCTV/Edge Cameras] --> Edge[Edge AI Box/K3s]
  IoT[RFID/IoT/GPS] --> MQTT[MQTT Broker]

  CDC --> Lake[MinIO + Iceberg/Delta]
  Agent --> Lake
  Kafka --> Lake
  API --> Lake
  MQTT --> Lake
  Edge --> MQTT

  Lake --> Spark[Spark + Airflow]
  Lake --> Trino[Trino/ClickHouse]
  Spark --> Feature[Feast Feature Store]
  Feature --> ML[MLflow + Model Registry]
  ML --> Engines[Forecast/Slotting/Picking/VRP]
  Engines --> Apps[Dashboards + WMS/TMS/ERP APIs]
  Apps --> Users[Warehouse/Store/Okala/CEO]

  Apps --> Audit[Audit Log + RBAC]
  ML --> Monitor[Model/Data Drift Monitoring]
  Monitor --> Retrain[Retraining Workflow]
  Retrain --> ML

توضیح

داده شعب با Agent محلی buffer می‌شود و در صورت قطعی، پس از اتصال ارسال می‌شود.

ویدئو خام فقط در Edge پردازش می‌شود؛ به مرکز داده metadata/hit/event ارسال می‌شود.

مدل‌ها در MLflow نسخه‌بندی می‌شوند و featureها از Feast مدیریت می‌شوند.

خروجی AI به شکل API به WMS/ERP/TMS برمی‌گردد و هر پیشنهاد قابل override است.

قطعی اینترنت

در صورت قطع ارتباط شعب/انبار با مرکز:

POS و عملیات حیاتی با cache محلی ادامه می‌یابد.

Edge AI رویدادها را locally queue می‌کند.

WMS local rules fallback فعال می‌شود.

پس از اتصال، reconciliation و replay انجام می‌شود.

05. قالب مدل ROI

فرمول‌های پایه

صرفه‌جویی نیروی انسانی = ساعات کاهش‌یافته × نرخ هزینه ساعتی × تعداد روز عملیاتی

صرفه‌جویی خطا = تعداد خطاهای کاهش‌یافته × هزینه متوسط هر خطا

درآمد بازیابی‌شده از OOS = کاهش OOS × فروش بالقوه × margin

کاهش خواب سرمایه = کاهش موجودی متوسط × هزینه سرمایه

صرفه‌جویی حمل = کاهش km/order × هزینه هر کیلومتر × تعداد سفارش

05. برنامه مدیریت تغییر

اصول

AI باید به عنوان «کمک‌کار عملیاتی» معرفی شود، نه جایگزین مستقیم پرسنل.

هر پیشنهاد سیستم باید قابل توضیح و قابل override باشد.

پاداش عملیاتی باید به KPIهای درست وصل شود، نه صرفاً استفاده از سیستم.

اقدامات


| مرحله | اقدام |
| قبل از پایلوت | جلسه توجیه، baseline شفاف، انتخاب champion از پرسنل |
| هفته ۱-۴ | آموزش کوتاه، حضور تیم پشتیبانی در محل، جمع‌آوری feedback |
| هفته ۵-۸ | اصلاح UX و SOP، تعریف داشبورد adoption |
| هفته ۹-۱۲ | پاداش برای تیم‌هایی که KPI بهبود داده‌اند، مستندسازی درس‌آموخته |
| بعد از پایلوت | Scale فقط با تایید کاربران عملیاتی و مالک کسب‌وکار |
