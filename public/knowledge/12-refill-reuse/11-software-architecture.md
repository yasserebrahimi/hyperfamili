# معماری پیشنهادی نرم‌افزار و کنترل؛ از ایستگاه تا مرکز

## طراحی مستقل از سازنده دستگاه
این معماری درباره دستگاه خودِ گرین‌چی نیست. مشخصات اتصال آن معلوم نشده و باید از سازنده دریافت شود. برای پایلوت، خرید ابزار یا جایگزینی ERP پیش‌فرض نیست؛ ابتدا رابط‌های موجود بررسی شوند.

```text
کاتالوگ و قیمت مصوب ──> سرویس پیکربندی/نسخه ──> ایستگاه شعبه
                                                      │
کنترل ایمنی محلی <── حسگر/ابزار سنجش ──> ثبت خروج واقعی │
                                                      │
ایستگاه ── رویدادهای یکتا و صف پایدار ──> دریافت مرکزی │
                                                      │
رسید یکتای پرکردن ──> صندوق/درگاه مجاز ──> نتیجه تسویه
                                                      │
                            موجودی، کیفیت، پشتیبانی و تحلیل
```

## اجزای حداقل
هسته کاتالوگ/فرمول؛ تنظیم ایستگاه/مدار و قواعد مجاز؛ ثبت لات و موجودی؛ تراکنش پرکردن؛ رابط صندوق؛ برچسب؛ پنل کارکنان؛ پرونده کیفیت/نگهداشت؛ گزارش مدیر. ابتدا می‌توان یک سرویس ماژولار قابل پشتیبانی ساخت؛ ریزخدمت یا GPU نیاز خودکار پایلوت نیست.

## لایه محلی
ماشین حالت تراکنش و قفل‌های ایمنی مستقل از ابر باشند. داده عملیات ابتدا پایدار ثبت، سپس ارسال شود. پس از ری‌استارت، وضعیت نامعلوم به ادامه خودکار پرکردن تبدیل نشود. نسخه تنظیم و آخرین اندازه‌گیری همراه هر معامله بماند.

## آفلاین؛ به معنی همه‌چیزمجاز نیست
در قطعی ارتباط با مرکز، فقط کارهایی مجاز باشند که وضعیت قیمت/محصول و سقف اعتبار پیکربندی آنها طبق سیاست معتبر است. وقتی وضعیت مجوز کیفیت، سنجش یا قیمت نامعلوم/منقضی است، فروش متوقف شود. پرداخت نیازمند تأیید مسیر مجاز خود است؛ قطع اینترنت مجوز فروش اعتباری یا ذخیره اطلاعات کارت ایجاد نمی‌کند.

## نقش‌ها
کارمند خدمات: ثبت و کمک، بدون تغییر فرمول یا قیمت.

کیفیت: آزادسازی/تعلیق لات و مدار، بدون دست‌کاری سابقه فروش.

مالی/قیمت: نسخه قیمت و رسیدگی مالی با ردپا.

تعمیرکار: وضعیت سرویس و آزمون، بدون دسترسی غیرضروری به داده مشتری.

مدیر: گزارش و تصمیم دامنه اختیار؛ نه حذف قفل ایمنی.

## امنیت و تغییر
هویت منحصر دستگاه، ارتباط محافظت‌شده، حداقل اختیار، تغییرات نسخه‌دار و قابل بازگشت، کنترل دو مرحله‌ای برای تغییر حساس و ثبت غیرقابل‌انکار رخداد پیشنهاد می‌شود. حذف یا ویرایش معامله قطعی به‌جای سند اصلاحی مجاز نباشد. هیچ API جعلی از سازنده یا پروتکل تأییدنشده فرض نشده است.
